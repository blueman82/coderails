# hooks/patches/

These files hold the exact patch text for
`hooks/scripts/remember_inject_cap_guard.py`. That `SessionStart` hook can
restore the memory-injection byte cap after a **remember** plugin update.

**The guard only warns by default.** It does not use this patch text until
you opt in. The remember plugin has another maintainer, so the default
guard reports an absent cap once per plugin version and changes no file.
Set `REMEMBER_INJECT_CAP_AUTOWRITE=1` in the `env` block of `settings.json`
to enable the patch. The matching and re-derivation rules below apply to
that opt-in path.

| File | Role |
|---|---|
| `remember_inject_cap.vendor.txt` | The **search** block — the remember plugin's unpatched memory-injection `for MFILE` loop, exactly as the vendor ships it |
| `remember_inject_cap.patched.txt` | The **replace** block — the same loop with the `REMEMBER_INJECT_MAX_BYTES` truncation applied |

### Scope: the loop only, not the enclosing `if`

Both blocks cover the `for MFILE ...; do ... done` loop and nothing else. They
deliberately stop short of the surrounding `if [ -n "$HAS_MEMORY" ]; then` and
its closing `fi`.

Version 0.8.9 changed the area after the loop. The original patch blocks
covered the whole `if` statement. A vendor edit anywhere in that body then
caused a shape mismatch. Version 0.8.9 added a rotated-archives section
between `done` and `fi`, so the guard refused the old block. The loop was
byte-identical in versions 0.8.3 and 0.8.9. A block limited to that loop
matches both versions and preserves the vendor's added section.

Keep both blocks at the same scope. If `vendor.txt` covers less than
`patched.txt`, the patch can add a duplicate `if` and an unmatched `fi`.
The guard's `head -c` check does not catch this Bash error. Run `bash -n`
on the patched file to detect it.

An earlier vendor loop uses the same `for MFILE in ...` line to compute
`HAS_MEMORY`. The loops differ on the next line: one uses
`[ -f "$MFILE" ]` alone; the other adds `&& [ -s "$MFILE" ]`. The
eight-line block therefore matches exactly once. Do not shorten it. The
Python guard requires one match before writing.

## DO NOT EDIT, REFORMAT, OR COMMENT THESE FILES

Both `.txt` files are **byte-exact match keys**, not documentation.

The guard searches `session-start-hook.sh` for the exact line sequence in
`vendor.txt`. It replaces that whole block with `patched.txt`. An added
line, changed indent, wrapped comment, or removed trailing space breaks
the match. The guard then refuses to patch and asks for manual
re-application. It has no fuzzy fallback. Line-number and context-diff
patches can silently drift after a vendor update; a literal match fails
visibly.

So: **no header lines, no provenance comments, no "generated by" banners inside
either file.** That is what this README is for.

The Python tests check replacement against isolated plugin fixtures. They also
execute the patched vendor loop to check the byte cap. The patch text must
still match the real vendor file exactly when an owner applies it.

## Provenance

`vendor.txt` is a **reconstruction**, not an untouched upstream file. The
cap was first applied by hand to the version-pinned plugin cache. No
original copy was kept. The vendor block was recovered by reversing that
change in the live file. `patched.txt` came from the live file after the
hand change.

A round trip checked the pair. Replacing `patched.txt` with `vendor.txt`
in the live file, then running the guard, reproduced the live file
byte-for-byte. `hooks/scripts/tests/remember_inject_cap_guard_test.py`
checks isolated plugin fixtures. It does not check the live cache on each
run.

## Editing the patch text legitimately

If the vendor changes the injection loop, derive both files from the new
source. Do not hand-edit the old blocks. Copy the new unpatched loop
verbatim to `vendor.txt`. Apply the cap to a copy for `patched.txt`. Run
the test suite.

Before committing a re-derivation, verify against the real plugin file, not
just the fixtures:

1. Run
   `REMEMBER_HOOK_FILE=<copy> REMEMBER_INJECT_CAP_AUTOWRITE=1 python3 hooks/scripts/remember_inject_cap_guard.py`
   against a **copy** of the live `session-start-hook.sh`. The guard must find
   exactly one vendor block and apply the patch. It refuses zero or multiple
   matches.
2. Run `bash -n` on the patched copy. This catches a mismatched-scope block
   pair that the guard's `head -c` evidence check cannot catch.
3. Execute the patched loop against a memory file larger than the cap and one
   smaller, and confirm the truncation marker appears for the first and not the
   second. Grepping for the `head -c` line proves the text landed, not that
   truncation works.

Changing only the NOTE comment in `patched.txt` does not update an
installed patch. The guard detects the cap through
`head -c "$REMEMBER_INJECT_MAX_BYTES"`, not the comment. It leaves an
already-capped file alone until a plugin update removes the block and the
guard applies it again.
