## Promoted lessons

### A green test suite is not evidence the gate works — only a negative control run against the code that HAD the bug is

- **Failure mode:** Real defects in infrastructure ship while a test suite reports green because the suite was authored by the same process that wrote the code, so it encodes the same blind spot. A green suite cannot catch bugs the author couldn't imagine. Worse, a broken fix can also pass 39/39 green and leave a regression undetected until an independent reviewer exercises it.
- **Lesson:** For any gate, guard, or check, the only evidence that counts is the **negative control** — run the check against the code that actually had the bug and watch it **fail**. "Tests pass" answers "is the code self-consistent?", never "does the gate do its job?" A control that has never failed is decoration. Two corollaries: (1) **Verify the control reverted** — `git stash push` on a committed file is a silent no-op; use `git checkout <base-ref> -- <file>` against an explicit ref and confirm the revert took before trusting any control. (2) **Evals authored post-hoc share the implementer's oracle** — derive every assertion from the bug report's goal state, never shell out to the repo's own test suites. Reviewers' independent exploit inputs are worth more than any assertion the author could invent.
- **Evidence:** Recurred 7 times across 7 distinct sessions (fb2bfec4, 2e82b342, 007e525b, bc0e6ad9, 75fa2e68, f876b596, 0692aeab). Session fb2bfec4 had two real bugs live at 39/39 green on main; first fix shipped a worse defect also at 39/39; only independent review caught both. Loop 1cc4c7d0 had five frozen evals with correct intent but wrong observation mechanisms, all invisible at freeze because the smoke-run only saw the fail side (pre-build). Loop 75fa2e68 proved the sharpened rule: a check only observed failing has not been shown to discriminate — exercise the formula against a **synthetic pass-shaped input** too at freeze time.
- **Promotion date:** 2026-07-20

### A frozen, blind-authored check can itself be defective — validate each scripted check's discriminating power before freezing

- **Failure mode:** A frozen check that has never produced both a pass and a fail is not yet a check. An awk formula exiting 1 unconditionally, a proof cmd whose grep pattern never occurs in its input, a process substitution unreadable in a non-bash shell — all are silent defects invisible at freeze if the check is only observed failing (pre-build code, everything fails for the intended reason). Checks with correct intent but wrong observation mechanisms can ship and leave suites vacuous.
- **Lesson:** At freeze time, run each scripted `cmd` and `negative_control` once for real in the actual execution shell, and smoke-test both environment plumbing and formula correctness. If the check carries optional `fixtures` (synthetic pass-shaped and fail-shaped inputs), validate the formula can discriminate — require opposite exit codes from good vs bad fixtures. A check observed only failing is half-validated at best; exercise both sides at freeze. Amendment path (not rewrite): recorded reason, assertion unchanged, fresh re-grade if a verdict exists. For agent-run evals, smoke-test the grader's prompt structure and confirm it receives only the artifact references, never the implementation conversation — the author is the least able to see their own shims.
- **Evidence:** Recurred 4 times across 5 distinct sessions (8b69e779, bc0e6ad9, 75fa2e68, 1cc4c7d0, 5f525531). Loop 8b69e779 had four frozen checks broken in ways unrelated to the artifact they judged; loop bc0e6ad9 had three frozen evals whose `cmd` had never been run and would fail on first execution (reporter flag doesn't exist, npm workspaces mismatch, gate self-blocks). Loop 1cc4c7d0 had five instances with intent-correct-mechanism-wrong, invisible at freeze — the two-sided smoke-run would have caught all five. Loop 5f525531 froze an eval asserting a regression lock would ship in one file when the fix correctly chose another; smoke-run on synthetic fixtures would have discriminated.
- **Promotion date:** 2026-07-20

### The Bash tool's working directory drifts between calls to whichever sibling worktree was most recently entered — anchor every command

- **Failure mode:** In multi-worktree sessions, a shell's cwd silently resets between tool calls to a different worktree of the same repo (whichever was most recently entered). A worker's test run can execute against the wrong repo's code, test assertions pass with wrong cardinality, and git status comes back suspiciously clean. The drift is transparent to the caller unless the output is cardinality-sensitive (test counts, assertion totals, list lengths) or the cwd is visibly wrong.
- **Lesson:** Never rely on cwd persistence between Bash calls in multi-worktree loops. Start every command with an explicit `cd <absolute worktree path> &&`, use `git -C <absolute path>`, or run git/file commands with absolute paths throughout. Treat known-cardinality outputs (test counts, assertion totals) as identity checks — a mismatch means you may be in the wrong tree. Edits with absolute file paths are immune to cwd drift; a probe pinned to a coordinate the repo can move under (line numbers via `sed -n N`, whole-file greps, working-tree path) is a stale instrument.
- **Evidence:** Recurred 6 times across 5 distinct sessions (0767967d loop ordinal 1; 8a43eccc; eafadd31; 47859e78; b5fe4e97). Session 0767967d had a worker's test run against the wrong repo (caught via assertion-count mismatch) and orchestrator shell reset to a sibling worktree across multiple turns; both cases re-anchored with explicit `cd <absolute>`. Loop 47859e78 had orchestrator shell reset to a sibling worktree on nearly every Bash call while the work lived in a different worktree; loop b5fe4e97 had orchestrator shell reset on essentially every call while work lived in a sibling worktree. All cases resolved by explicit `cd <absolute>` or `git -C <absolute path>`.
- **Promotion date:** 2026-07-20

### A worker's "all N items done" report on a multi-item fix list is a per-item claim, not one claim — verify each item against the merged artifact

- **Failure mode:** A multi-item fix (N distinct items) gets a single "done" report that collapses N independent claims into one. At the merge boundary, re-reading origin shows the report was partial: the first "done" had the gate fix but not the price or sanitisation; a later "C fixed" had the guard but the numeric leaves were still wrong. Each report was two-thirds true because messages crossed in flight and "done" referred to an earlier, narrower ask. Worse, when a report is fully honest and the worker's self-verification genuinely passed, that is not evidence of completeness — it is evidence the worker's oracle and its scope agreed with each other. An independent reviewer with a different lens catches defects nobody thought to ask for.
- **Lesson:** When a fix list has N distinct items, apply Phase 12 (verify against merged state) **per item**, not per report. At merge boundary, grep/reproduce each item against the merged SHA by name (the price row, the sanitise call, the specific guard, the specific test). Expect "done" to mean "the last thing I understood you to ask," especially amid mailbox-crossing — multi-item fixes nearly always need one more verify-and-nudge round than the report implies. The cost of re-verifying each item is one grep; the cost of merging 2/3-done is a reopened crash class.
- **Evidence:** Recurred 2 times (47859e78 loop ordinal 1; f876b596 ordinal 2). Loop 47859e78 had three separate "done" reports each two-thirds true on a 4-item miner fix; each partial closed by re-reading origin and sending a per-item nudge. Loop f876b596 saw two independent reviewers find real defects (doc row contradicting its own sibling paragraph, test missing the actual-failure ordering) in PRs with honest, self-verified green reports whose scope simply hadn't asked the right question yet.
- **Promotion date:** 2026-07-20

### Two spawned agents can receive the same unit's brief, or a worker can self-identify under the wrong name — resolve ownership by artifact, never by the name label

- **Failure mode:** In a parallel dispatch wave, two spawned agents both received the same unit's brief despite having distinct names, leaving a different unit unowned; re-dispatching that unit off a stale "no branch exists yet" check (run before the original agent's branch had appeared) caused two instances to build the same unit and collide on one branch. Related but distinct: workers self-misidentify as a different, unrelated unit when they inherit the orchestrator's own working-directory context rather than a clean one, and completion reports routinely cross in flight with the next instruction, making "already done" ambiguous. In one case a reviewer never produced a report at all after two idle periods — an absent-report variant with no artifact to check.
- **Lesson:** After dispatching a parallel wave, confirm ownership by artifact, not by name: before re-dispatching a unit believed unowned, re-run ground truth (worktree/branch listings, open PR state) at the moment of acting, and account for the lag between a worker starting and its branch or PR becoming visible. If a worker reports its brief doesn't match its name, resolve by the brief's content and the artifacts already on disk. Prefer unit-specific identifiers that can't collide. When a report and a new instruction cross in flight, reconcile by re-reading the actual current state rather than trusting either side's message as true or false. **Related but distinct — the no-artifact case:** when a worker produces no artifact at all (an idled reviewer that never reports), there is nothing to resolve ownership against, so the rule above cannot apply. Don't re-ping an idle worker more than once; if its scope is small and already fully read, do that piece of work inline instead of looping on re-pings — and if its output would have been an input to a gate or an artifact you are about to post, say plainly in that artifact which dimensions went uncovered, rather than letting the fallback read as a completed review.
- **Evidence:** Occurred across 9 distinct sessions, including the original (f87a0a2e, then recurred in 13b7e758, 1cf76302, 0767967d, 8a43eccc, 5b916f1a, eafadd31, 47859e78, 8b69e779). Instances ranged from a genuine same-branch collision (f87a0a2e) to pervasive mailbox-crossing resolved by re-reading origin at the moment of acting (47859e78, "49 awaiting-input stops in one loop, most from this crossing") to a reviewer that idled twice and never reported (5b916f1a, resolved by substituting an inline read-only pass for a small, already-read review dimension).
- **Promotion date:** 2026-07-27

### A concurrent actor can merge into the same files, take a reserved version number, or move the target you're mid-edit on — sweep for other in-flight work at intake, not just once

- **Failure mode:** A staged plan from another session began executing concurrently and merged into the same files this work was editing, taking a reserved version number and breaking a version lockstep; the collision was discovered only by accident. The same hazard recurred repeatedly in other forms: a concurrent PR landing on the same shared file mid-task, several PRs landing under one long task in sequence forcing repeated re-fetch-and-fold, and — the least visible variant — a parked, ownership-claimed piece of work that has no open PR and no live session, discoverable only by searching for the specific symbol or file it claims, not by checking PRs or sessions alone.
- **Lesson:** At intake, sweep for other in-flight work on the same subsystem: list any staged/pending plans and read ones touching the same files, list open PRs against the same files, and re-verify at the moment of acting rather than trusting an earlier read. Treat any reservation (a version number, a claimed slot) recorded in a frozen artifact as a claim that can be raced — re-verify it right before consuming it, and expect the shared base to move under a long-running task (re-fetch before every merge). Critically, also search any persistent memory or task-tracking index for the specific symbol or file a candidate touches — a piece of work can be claimed by another owner with no open PR and no live session to reveal it, and that is invisible to a PR/session sweep alone.
- **Evidence:** Occurred across 4 distinct sessions where the sweep failed to prevent real damage or rework, including the original (13b7e758, then recurred in 1cf76302, b5fe4e97, 8b69e779). Four further sessions (f876b596, 17c78b4e, 0767967d, eafadd31) ran the sweep and it worked — it correctly flagged a live concurrent collision or a parked-ownership claim, and the collision was absorbed cleanly with no rework — confirmations the mitigation works, not additional instances of the hazard defeating it. Session b5fe4e97 saw the shared base move three times in one task, two of the three landing directly on the same subject matter being worked; session f876b596 extended the sweep to the parked-ownership variant after a genuinely-valid-seeming fix target turned out to be another arc's explicitly claimed main item — a 33% false-work rate avoided by one grep, which is why it counts as the mitigation working rather than failing.
- **Promotion date:** 2026-07-27

### Never edit the implementation to make a failed or qualified check pass by emitting the string it looks for — that changes what the system says about itself, not what it does

- **Failure mode:** An evidence check required proof a component ran outside a particular execution path; no such evidence existed in the logs because the wrapper only captured what a child process printed, and the check came back qualified on indirect reasoning instead. The reflex was to add a banner line that printed the exact string the check was looking for — which would have been forgeable by hand, executed unconditionally regardless of whether the real mechanism ran at all, and timestamped after grading so it couldn't even have been the evidence a frozen check saw. A related recurrence: three evals froze a hardcoded path to one checkout and false-failed because the actual fix lived on a different branch/worktree — the honest fix was to grade against the real merge-target content and disclose the correction, not to edit the evals to pass.
- **Lesson:** When a check comes back failed or qualified, the only honest moves are: report it at that grade, fix a real defect in behavior that the check exposed, or name the observability gap as future work. Never edit the implementation so it emits the string a check greps for. Two diagnostics: "does this change what the system DOES, or only what it SAYS about itself?" — if only the latter, it's gaming. "Could this evidence be forged by the very component under test?" — if the artifact under test writes its own proof, that proof is self-attestation, not evidence. Separately, when a frozen check fails because it's pointed at a stale copy of the code rather than the real fix location, the fix is to grade against the actual merge-target content and disclose the correction — never to weaken or edit the check itself to force a pass.
- **Evidence:** Occurred across 2 distinct sessions, including the original (b5fe4e97, then recurred in 5f525531). In b5fe4e97 the gaming attempt was caught only by a direct owner challenge before it shipped; in 5f525531 three evals hardcoded a stale checkout path and were correctly re-graded against the real branch content rather than edited to pass.
- **Promotion date:** 2026-07-27

### A sequencing or ordering decision you can already back with evidence you verified yourself is not a question for someone else — and an unnecessary pause lets the world move and decide it for you

- **Failure mode:** Facing two pieces of in-flight work with a guaranteed conflict, all the facts needed to decide (which was ready, which anchor was unambiguous, which ordering was reversible) had already been independently verified, yet the decision was twice deferred to a human as if it were a new, out-of-scope question. In both cases, the deferral bought nothing but delay — the outstanding work resolved itself while the question sat unanswered, once by a concurrent merge landing anyway. The same shape recurred as pervasive low-level over-asking across many decisions (fix ordering, whether to re-review before merging, scope framing) in a single high-autonomy task, each individually verifiable and each still escalated.
- **Lesson:** A decision belongs to you, not to escalation, if you can back it with something you personally verified. Test: can I back this call with evidence I checked myself? If yes, decide it, record the decision and reasoning, and move — don't defer a scheduling detail as if it were a new question. An unnecessary pause is not neutral: shared state keeps moving while a question sits open, so the eventual answer can already be stale or moot by the time it arrives, and the pause has cost real attention for nothing.
- **Evidence:** Occurred across 3 distinct sessions, including the original (007e525b, then recurred in 7e077d6c, 0692aeab). Session 0692aeab was the most severe instance on record — 23 awaiting-input stops and 11 hard-stops in one loop, the highest count recorded, of which at least 4 were confirmed to be in-envelope steps whose safety was already verifiable that session (fix sequencing, whether to re-review before merge, custody-fork scope, post-merge conflict resolution) — flagged explicitly by the person being asked ("aren't you in a loop?").
- **Promotion date:** 2026-07-27

### A confident negative claim from one surface ("never happened", "nothing logs this", "not supported") can be simply wrong if you never checked where the component actually writes or documents itself

- **Failure mode:** A component believed dead was diagnosed by grepping the one log file that seemed like the obvious place to look; zero hits led to a confident, reported conclusion that it had "failed silently and never escalated." That was false — escalation used a completely different write path that the grep never touched, and the real record, sitting there the whole time, named the exact cause. The same shape recurred with documentation standing in for a log: a flag's absence from a tool's help text was nearly read as proof the flag was rejected, when a live invocation showed it was in fact accepted, just undocumented.
- **Lesson:** A zero-hit grep, or an absence in one document, proves only that you looked in one place — nothing more. Before asserting a negative ("never happened," "isn't supported," "nothing logs this"), find where the component in question actually writes or actually executes, and check there directly rather than trusting a proxy surface (a log redirect, a help page) to stand in for the real one.
- **Evidence:** Occurred across 2 distinct sessions, including the original (7e077d6c, then recurred in 0692aeab). In 7e077d6c the wrong-surface conclusion was already stated in a user-facing report before the correction; in 0692aeab the same shape (documentation-absence read as rejection) was caught before a working flag was removed from a script on the strength of it.
- **Promotion date:** 2026-07-27

### A cleanup or teardown step is a state change that other automation may be watching as a trigger condition — check what it satisfies elsewhere before declaring a task complete

- **Failure mode:** A routine teardown step (moving several items into an archival/decayed state) was correct and mandated on its own terms, but that exact write happened to be the last unmet condition of a separate, dormant automation's graduation predicate — flipping it live and arming a scheduled run that carried a known-exploitable check nobody had re-examined for this new context. The task would have declared itself complete without ever noticing it had just activated something else. The same shape recurred in a sharper form: two teardown writes in one task each individually satisfied a different downstream gate's precondition, one of which would have silently blocked the task's own completion declaration if not caught by reading the gate's source first.
- **Lesson:** A teardown or cleanup write is not mere bookkeeping — it is a state change to a file some other piece of machinery may read as a precondition. Before declaring a task complete, work out what watches the files this teardown just touched — grep the repo for readers of each touched path, and READ THE SOURCE of any gate, hook, or scheduled job that names one, checking its trigger predicate against the state you just wrote — then re-evaluate whether the write satisfied a predicate you didn't intend to trigger. A dormant automation is dormant because of a specific condition, and a routine, unexamined write is exactly the kind of thing that quietly closes it.
- **Evidence:** Occurred across 2 distinct sessions, including the original (7e077d6c, then recurred in bedcb0d4). Session bedcb0d4 added the sharper variant: teardown ORDER itself matters — a check that names a path a teardown is about to delete must run before the deletion, and a terminal status write must land before the completion gate that reads it is triggered.
- **Promotion date:** 2026-07-27

### A destructive proof that temporarily disables a guard, even with an intended restore, must never run on a working tree another agent might also be editing concurrently

- **Failure mode:** A worker and an orchestrator both independently ran a destructive proof (briefly neutralizing a guard to observe unguarded behavior, then restoring it) on the same shared working tree at the same time. No permanent damage resulted, but one restore silently reintroduced a stale copy of a file instead of the original tracked version — caught only because the restore was independently checked afterward, not because the restore itself reported any failure. The same shape recurred with a worker reporting its own restore as a confirmed "clean revert" when it was not — the working tree still carried the mutation at a later checkpoint, caught only by an unrelated process incidentally surfacing the tree's real state.
- **Lesson:** A proof that disables a guard, even briefly and even with a planned restore, must run on a throwaway copy of the affected file(s) or a dedicated isolated workspace — never a working tree another agent might also be touching. If a shared tree is genuinely unavoidable, treat the restore itself as an unverified claim until independently checked (diff against the pre-mutation state) — a restore's own "success" report is a claim like any other tool output, not evidence.
- **Evidence:** Occurred across 2 distinct sessions, including the original (0692aeab, then recurred in a05e0075). Session a05e0075 was the sharper recurrence: the worker's self-reported "confirmed clean revert" was false, and the mutation was still present in the shared working tree at a later boundary check.
- **Promotion date:** 2026-07-27

### Shared state written as JSON can be silently corrupted by a concurrent writer racing your own edit — a dropped comma reads downstream as a blanked field, not as a parse error

- **Failure mode:** A guard reported a key identifying field as blank on a shared state file that visibly, on inspection, contained the correct value. The real cause was invalid JSON: a concurrent process (a linter, a hook, another tool) had written to the same file at nearly the same moment as an in-progress edit, dropping a comma between two keys — so the field-reading step silently failed to parse and returned empty, which the guard reported as a mismatch rather than a syntax error. This recurred identically, same day, same mechanism, on a different file under heavy concurrent-write activity.
- **Lesson:** When a guard reports a supposedly-correct field as blank or mismatched on a file you can see holds the right value, suspect JSON corruption before suspecting the field itself — validate the file's JSON syntax first; a parse error surfaces upstream as an empty or mismatched field, not as an explicit syntax error. Locate and fix the structural break (usually a dropped comma or brace from a racing write) rather than blindly re-writing the field. Do not assume a file is single-writer just because it is scoped to one task or session — other tooling can still write to the same path concurrently. Once corruption is CONFIRMED — you have validated the syntax and seen the parse error — prefer replacing the whole file content over a surgical in-place edit, since a surgical edit is what's most likely to race a concurrent write back into a broken structure. Do not invert that order: an external-modification signal on its own is a reason to re-read the file and re-validate, never a licence to overwrite it wholesale from an in-memory copy, which silently drops whatever a concurrent writer legitimately added.
- **Evidence:** Occurred across 2 distinct sessions, including the original (a05e0075, then recurred in 6ccd3c6a). Both instances diagnosed by validating JSON syntax first (revealing an exact line/column parse error from a dropped comma) rather than assuming the guarded field itself was wrong.
- **Promotion date:** 2026-07-27

### Write the exact field name and exact value a gate's parser reads, not a synonym that means the same thing to a human — even having just read this rule doesn't guarantee applying it at write time

- **Failure mode:** A completion declaration was blocked as unfinished for work that was genuinely done — merged, deployed, and verified live. The status had been recorded with a field name and values that were factually accurate and read correctly to a person, but the gate consuming that record used a different field name and a narrow, exact allowlist of values; anything else parsed as empty and blocked. The identical mistake recurred in the same lesson family in a different session: descriptive-but-nonconforming values were written again, and — even more pointedly — recurred a second time in the very same session that had already read this exact lesson earlier, and still wrote synonyms instead of the gate's literal accepted values.
- **Lesson:** Before writing any field a gate consumes, read the gate's own parsing logic and match it exactly — key name and permitted value, never an equivalent-sounding substitute. When a gate blocks work you believe is finished, the first hypothesis should be that the record is malformed, not that the gate is wrong — check the consumer's exact allowlist for the field before arguing with the verdict. Having previously read this rule is not the same as applying it at the moment of writing the field; re-check the literal allowlist every time, not from memory.
- **Evidence:** Occurred across 2 distinct sessions, including the original (a4c9c07c, then recurred in 727e0f67). Session 727e0f67 is the sharper instance: the same session had already read this exact standing lesson earlier and still wrote descriptive synonyms instead of the gate's literal accepted values.
- **Promotion date:** 2026-07-27
